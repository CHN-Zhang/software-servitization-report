# 图存储、检索和保存恢复验证

日期：2026 年 10 月 29 日。

## 这次的结论

已在固定版本 Mandol 上运行真实的 SemanticGraph、SemanticMap、FAISS、BM25 和 RocksDB。常驻模式及冷热存储模式下，合并结果可以写入、被检索，并在关闭图资源后由新进程加载，恢复后的数据和检索结果与保存前一致。

这次不是 AST 或写入替身检查。唯一替换的是嵌入模型加载器，使用6维确定性特征向量，不下载模型，也不调用API。因此验证的是图、索引与磁盘数据的连接和一致性，不是语义检索效果或合并判定质量。

## 测试场景

使用原 L1ExtractionResult 构造两条已知可合并的文本：“Shanghai Friday”和“Shanghai Friday; return Sunday”。主体信息由测试明确提供。原型选择信息更多的后一条，并汇总 raw_a、raw_b 两个来源。

合并结果通过原 HierarchicalAutoBuilder.add_to_semantic_system() 和 GraphWriteQueue 写入真实图，不手写一个模拟写入流程。另外加入基础记忆和对照节点，合计5个节点、3条关系。两条 DERIVED_FROM 边由测试显式添加，只用于验证真实图关系，不表示原合并组件已经自动维护来源边。

删除一个对照节点后应剩4个节点、2条关系、4条FAISS向量。被合并但未选中的a从未写入图，因此本场景不是已有历史图的节点迁移测试。

## 已通过的检查

| 项目 | 检查内容 |
|---|---|
| 入图与空间 | 节点数、边数、L0/L1空间归属、来源列表和合并元数据 |
| FAISS检索 | 在L1空间查询return，首位是包含补充信息的b |
| BM25检索 | 使用原BM25代码和其自带正则分词回退，查询return可以命中b |
| 删除与残留 | 对照节点从内容、图、关系、空间和FAISS中移除 |
| 常驻模式保存恢复 | 保存实际图、元数据、向量和索引，关闭资源后由子进程加载 |
| RocksDB换出 | 强制换出3条payload，图拓扑和索引保留，按需加载后状态不变 |
| 冷节点删除 | 先把删除目标换到RocksDB，确认磁盘中存在，再删除并确认磁盘无残留 |
| 冷数据快照 | 保存时仍有2条冷payload，随后在子进程恢复 |
| 恢复一致性 | 内容、来源与其他元数据、向量、边、空间、UID映射，以及检索ID和分数逐项比较 |
| 已保存的BM25索引 | 子进程单独加载保存的BM25文件并查询，不只依赖重新建索引 |

定向测试的常驻和RocksDB两种模式都通过。同时运行原项目 `tests/test_rocksdb_tiered_cache.py`，结果为 **19 passed**，其中还覆盖自动换出、冷数据更新删除、快照等待及兼容性等情况。上游这些测试也使用模型替身，不能当作真实模型效果验证。

## 怎样复查

测试脚本是 `verify_graph_storage.py`，环境依赖记录在 `requirements-graph-test.txt`。需要 Python 3.12，并按README准备相邻的固定版本Mandol源码。

```powershell
python -m pip install -r requirements-graph-test.txt
python verify_graph_storage.py
```

脚本会在课程仓库上一级的tmp目录中建立独立的运行目录；运行前请确保该tmp目录存在。保存前后的状态、图快照、RocksDB文件和子进程日志均在该目录中。汇总记录为 `results/graph_storage/verification.json`，里面记录本次实际路径、依赖版本和源码哈希。

本次实际环境位于工作目录的 `.venv-mandol`，没有修改系统Python或上游源码。安装时发现最新SciPy与NumPy 1.x冲突，最终使用NumPy 1.26.4、SciPy 1.15.3、scikit-learn 1.7.2；其他主要版本见结果JSON。完整执行日志和上游测试结果保存在同一结果目录。

## 还不能得出的结论

- 没有证明真实语义模型会正确判断重复、条件、否定和时间变化。
- 测试显式提供主体信息，尚未解决原L1流程不传user_id的问题。
- 没有自动生成L2或执行完整三塔检索、SPLADE和重排序。
- 没有验证大规模性能、异常断电、并发历史图合并或实际内存收益。

因此目前可以说：“合并结果通过了真实图、检索索引和保存恢复的一致性检查。” 还不能说整个超长记忆增强功能已经全部完成。
