# L1 去重改进的可行性检查

日期：2026 年 10 月 29 日。

补充：以下记录的是最初的组件替身检查。随后完成了真实图、索引和保存恢复检查，详见[图存储与恢复验证](图存储与恢复验证.md)；语义判定和主体信息传递等问题仍需处理。

## 结论

这个修改有明确的接入位置，原有结果类型也能承载合并后的内容和来源，因此可以继续做。但目前原型不能直接接上就认为完成，需要补主体信息的传递、语义安全判断和完整系统验证。

## 这次怎样检查

新增 `test_feasibility.py`，从固定版本源码提取原 L1 结果类型、L1 提取方法、默认 L2 聚合方法和写入适配方法执行。模型返回固定文本，提示词管理和写入端使用替身。写入方法中的 MemoryUnit 构造被记录对象代替，没有实际运行 SemanticGraph、向量生成或 RocksDB。

这不是效果评测，而是组件连接检查；测试通过只说明对应的数据传递符合预期。

运行：

```powershell
python -m unittest test_feasibility -v
```

## 检查结果

| 检查 | 观察到的结果 |
|---|---|
| 原提取方法生成的 L1 能否直接进入原型 | 元数据没有 user_id，原型会拒绝合并。这是待解决的问题，不是功能成功。 |
| 补入已确认的主体范围后，原数据类型是否兼容 | 原型输出仍为原 L1ExtractionResult，能选用更完整文本，汇总来源，并且不修改输入对象。 |
| 合并结果能否继续交给默认 L2 聚合 | 原 L2 方法收到保留后的文本，source_l1_uids 指向保留的代表 ID。固定的 L2 返回值没有验证摘要质量。 |
| 来源能否进入原写入流程 | 原写入适配产生的请求携带来源并集和来源会话列表；未实际执行入图、索引及持久化。 |
| 不同用户和结构化结果是否被保守处理 | 原型不合并。但这也意味着它暂时不支持这些输入。 |

以上5项检查通过，其中第1项是确认阻碍接入的问题确实存在。

## 为什么技术上可以做

`HighLevelMemoryBuilder._build_hierarchical()` 中已经有 L1 去重之后、L2 聚合之前的处理位置，可以复用流程，不必重新做整个记忆系统。

`L1ExtractionResult` 是数据类，已有内容、来源列表和元数据字段。代表选择和来源汇总不要求重写其结构。原写入方法会把来源列表放入 MemoryUnit 元数据。

先在写入前处理新构建的 L1，可以暂时避开对历史节点、关系和持久索引的迁移。这不能证明对已有图进行整理也同样简单。

## 还需要解决的事情

1. **主体范围不能靠猜。** 原 L1 的 metadata 包含样式、日期和参与者等，并不自动包含 user_id。需要从调用者和 L0 来源传入已确认的范围。sample_id 可能只是样本标识，不能不加检查就当成用户身份；同一用户的记忆中也可能提到不同人物。
2. **字面包含不保证事实包含。** 条件、例外、否定和时间更新可能改变意义，分句后做集合包含不够。当前应把简单包含规则看作原型，不能称为安全的通用合并算法。
3. **跨会话合并需要保留语境。** 原型能记录多个来源会话，但代表仍只有一个 session_id。默认 L2 输入会使用这个代表会话标签，新增来源元数据不等于 L2 和检索已经正确使用全部时间、会话信息。
4. **来源列表只是粗粒度追溯。** L1 来源通常包含会话内多条基础记忆，汇总列表不能证明每条来源都支持摘要中的每个事实。
5. **结构化摘要尚未支持。** 原型遇到 is_structured 时跳过，因此不能把当前方案直接推广到所有构建样式。
6. **真实系统仍待验证。** 需要检查入图后的索引、检索、保存恢复，以及重建或重复执行是否产生冗余。当前没有证明总存储、内存或问答效果改善。

## 建议的最小实现顺序

先限定为同一明确主体范围内、普通文本的等价重复合并，打通来源汇总和原流程适配；遇到有条件或时间差异的内容先保留。再验证 L2、检索和保存恢复，最后考虑扩大到信息包含和跨会话合并。

目前适合在汇报中说：“已定位接入点并验证部分数据传递兼容性，发现主体信息传递等问题，完整实现仍在进行。” 不宜说“改进已经验证有效”。
